ONE FILE · ONE OWNER · FIFTY YEARS

Your life log, in one file you keep.

Lifelog keeps a journal of your days, the people and places in them, your health readings, your habits and the files you keep. Everything goes into one SQLite file, life.db, on your own disk. The file explains itself, so you can read it in fifty years, with or without this program.

WHAT IT KEEPS

What happened, and what you measured.

Lifelog is a life log and its backup. It keeps the record of your days in plain, typed tables. It does not guess, and it does not change your words.

A journal of day pages

One page for each day. Write in Markdown. A [[name]] links a person, a place or a page, and a #tag groups the pages.

People and places

Each person and each place has a page. Their names, birthdays and the days they appear in are kept as records, not only as text.

Health readings

Mood, weight, sleep, a blood test. Readings are never edited: a correction is a new reading that replaces the old one, so the history stays true.

Habits, without streaks

Check in each day: done or not done. A habit shows as “5 of 7 days”. There are no chains and no badges.

The files you keep

A voice memo’s transcript, a PDF’s text, a photo’s small picture. The original stays where it is, so the database stays small enough to copy.

Tasks and reminders

Write down what you plan to do and when it is due. Mark it done or skipped. The intent is kept beside what happened, and never mixed with it.

HOW YOU USE IT

One program, three ways in.

Lifelog is one Go binary. The browser, the command line and an AI agent all go through the same handler, so each one can do the same things, with the same rules.

Browserlifelog serve
Command linelifelog capture
AI agentlifelog mcp
One hypermedia APIevery action in one catalog
life.dbone SQLite file

The browser

Today at a glance: what is due, your habits, your newest pages. A calendar of each month, week and year. It works with no script, and on a phone.

The command line

Capture a line, read a day, check in a habit, keep a file or take a snapshot, from any terminal.

lifelog capture "Ran 5k with [[Sam]] #running" --mood 4

An AI agent, with your word

An MCP server lets a coding agent help you import old notes. The agent proposes each person, place and link. You say yes or no. Each row records which agent wrote it.

BUILT TO LAST

Made for the reader of 2075.

The largest risk to a lifetime of notes is not a broken disk. It is meaning that lives only in an application’s code, and an application that is gone. Lifelog is built against that risk.

  • One SQLite file. SQLite is a format that the Library of Congress recommends for keeping data. There is no server and no cloud account.
  • The file explains its records. Each table holds its own description. The rules that span tables are rows in the file. A stranger can read them with .schema.
  • The rules are in the database. A CHECK or a trigger refuses a bad write, whichever program tries it. The rules do not depend on Go.
  • Nothing is deleted. A removed page becomes a tombstone. A reading is corrected by a new reading. The record of your life only grows.
  • Snapshots you can trust. lifelog snapshot makes a dated copy and checks it with four integrity checks before it calls the copy good.
  • Your data stays yours. It runs on your machine. Your other devices connect to it with a token, over your own network.

FOR DEVELOPERS

An open contract, not a black box.

The database is specified on its own, in any language. Lifelog is one writer of it. You can read life.db with any SQLite tool, or build a different application around the same schema.

The schema

One canonical DDL: 15 strict, typed tables, a full-text index and 3 views. Every CHECK has a name. No JSON columns.

docs/schema/schema.sql

The decisions

Each rule has a recorded reason: why integer ids, why tombstones, why mood is a measurement. The alternatives that were cut are listed too.

The cookbook

The canonical reads and writes as SQL. A test suite runs every block, so the examples cannot go out of date.

WHAT IT IS NOT

Small on purpose.

Each table must earn its place. These things were considered and cut. Each one has a written reason, and a condition that can open it again.

Not includedWhy
Sync between copiesYour other devices are clients of one writer. A merge would remove the checked keys that keep the data correct.
A location trackA place has a point, and a photo’s place links its day. No minute-by-minute position is kept.
A photo archiveLifelog keeps the few photos that stand for a day. Your library stays in your photo tool.
A finance ledgerNotes about money stay text until a real need for numbers comes.
Encryption inside the fileThe file is plain on purpose, so it stays readable. Protect the disk with full-disk encryption.

GET STARTED

Build it, then write your first day.

You need Go 1.27 or later. You do not need cgo or the sqlite3 program: SQLite comes with the build. Lifelog runs on Linux and Windows.

# build
git clone https://github.com/alexradunet/lifelogdb
cd lifelogdb
go generate ./... && go build -o lifelog ./cmd/lifelog

# make life.db beside the program
./lifelog init

# write, then read
./lifelog capture "Ran 5k with [[Sam]] #running" --mood 4
./lifelog day --human
# open it in a browser: http://127.0.0.1:7777
./lifelog serve

# check in a habit
./lifelog done evening_walk

# keep a voice memo as its text
./lifelog file memo.m4a --text memo.txt

# a dated copy, checked before it is trusted
./lifelog snapshot --to ~/snapshots --human

# let a coding agent help you import
./lifelog agentic-init
